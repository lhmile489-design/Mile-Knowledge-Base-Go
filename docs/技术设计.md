## 1. 需求与技术约束

- 需求依据：PRD v1.0 全部 P0 功能与 NFR-PERF。
- 平台：只做 Windows 11 amd64（PRD Q1，decisions D-003）。运行时依赖系统自带的 WebView2。
- 必须解决的旧版性能根因：PRD 1.2 节 P-1 到 P-8。核心约束如下。
  - 全量遍历、全量序列化、逐文件的系统调用都放在 Go 侧做，并且有并发上限。
  - 索引增量落盘。
  - 流式输出增量渲染。
  - 长列表虚拟化。
- 必须复用的旧版资产：
  - 视觉令牌：旧版 `tokens.css`。
  - 图标库：phosphor。
  - 业务规则与数值：PRD。
  - 旧版单测：作为行为规格参考，不直接迁移代码。
- 用户在本阶段指定的选型（2026-11-18）：
  - 标题栏：无边框窗口，自绘按钮。
  - Markdown：在 Go 侧用 goldmark 渲染成 HTML。
  - 检索：用 SQLite FTS5，排序不必和旧版一致，尽量用 Go 提升性能。
  - API key：上限改为 2560 字节。

## 3. 系统边界与模块职责（阶段 07 细化）

单进程桌面应用：一个 Go 进程，一个 WebView2 窗口。没有服务端，没有网络服务；唯一的出站网络是模型供应商。

| 模块（建议包名） | 负责 | 不负责 | 输入 / 输出 | 信任边界 |
| --- | --- | --- | --- | --- |
| 前端（`src/`，React） | 布局、交互、虚拟列表、CodeMirror 编辑；注入 Go 给的 HTML，用事件委托接上链接、复制、引用标签等交互；按截图与 DESIGN.md 复刻界面 | 文件 IO、路径判断、权限、Markdown 解析、检索计算 | 只经 `src/lib/transport.ts` 调用生成的 `src/mygo.ts` | 不可信：所有入参由 Go 逐字段校验 |
| `internal/service` | mygo 绑定层：装配依赖、校验入参、把错误转成稳定错误码并脱敏、定向推送事件 | 业务计算 | 绑定方法、Channel、Event | 唯一 import mygo 的业务包（另外还有 `main`） |
| `internal/pathguard` | 路径的拼写层与真实路径层两道校验、知识库内判定 | — | 相对路径 → 规范路径 | 所有用户路径与 Agent 路径的唯一入口 |
| `internal/vault` | 知识库登记、知识库 id（与旧版算法一致，见 4.7）、脚手架、树、文本读写（UTF-8、BOM、换行还原、原子写入；Windows 下替换对短暂共享冲突重试）、revision、文件监听 | — | — | 写操作只经 mutation |
| `internal/index` | 扫描、分词、SQLite FTS5、链接图（增量）、健康检查、最近文档 | 正文持久化，正文永远在文件里 | 变更批次 → 索引；查询 → 结果 | 派生数据，可以删除重建 |
| `internal/mutation` | 变更计划、风险等级、事务（`.mile-kb/transactions/`）、操作日志、恢复、来源追踪 | — | 计划 → 报告 | 风险等级由 Go 计算；`.mile-kb/` 格式与旧版字节级兼容 |

依赖方向：`service → engine/agent/conversation/mutation/index/render/settings → vault → pathguard`。下层不 import 上层，也不 import mygo（文件监听由 service 注入）。

## 4. 关键链路

### 4.1 启动

1. 获取单实例锁（`App.RequestSingleInstanceLock`），失败则把焦点交给已运行的实例并退出。这也能避免 R-6 实测到的「短时间连开多个实例导致 WebView2 创建失败（HRESULT 0x800700aa）」。
2. 读应用设置；首次启动且没有新版设置时，执行旧版设置导入（4.7）。
3. `Theme.SetSource`；按主题设置 `BackgroundColor`（`#eceef1` / `#0e0f11`）；在建窗前注册图片协议。
4. 建无边框窗口（1440×900，最小 744×640），`OnReadyToShow` 时显示。实测进程启动到首帧前约 0.54–0.81 秒（spikes/r4-window）。
5. 打开上次知识库：先返回树的第一层，界面即可操作；文件监听快照和索引在后台建立，通过事件报告进度。

### 4.2 文件变更

- `WatchFiles`：普通模式，`Recursive`，`Ignore` 跳过 `node_modules` 与 `.git`，`MaxEntries` 设为 65536，去抖 50ms、最长延迟 500ms（R-1）。
- 收到一批事件后，按目录合并，在一个 SQLite 事务里只更新受影响的文档与链接边，再向前端推一次「目录变化」事件。不在每个文件上持久化整份数据（P-1、P-2）。
- 应用自己写入 `.mile-kb/` 和文档时也会触发监听；用 revision 比对过滤掉自己的写入，不重复处理。
- 知识库条目超过 65536 时 `WatchFiles` 会报 `ErrWatchLimit`，这时降级为 HintsOnly 模式加 Go 侧按目录比对（R-1 方案 b，实测同样零丢失），并在界面提示。

### 4.3 检索

- 预切词：中日韩文字切成二元组、英文按旧版规则切词，空格拼接后写入 FTS5 的 5 列（标题、标签、标题行、路径、正文），tokenizer 用 unicode61，不挂 external content。
- 查询：bm25 列权重 12/8/6/4/1；匹配字段、片段（命中处前后 60 字符）和高亮区间在 Go 侧计算。
- 实测（1 万篇）：p95 10.6ms，首建 1.33 秒、库 17.7MB，增量更新 1000 篇 204ms（R-2）。
- 每个知识库一个索引库，放在应用数据目录。旧版的 `index-<vaultId>.json` 不读取。

### 4.4 链接图

- 解析规则不变：相对路径 → 文件名 → 标题，唯一命中才算解析成功（PRD FR-LINK）。
- 实现：按「规范路径（含去扩展名）」「小写文件名去扩展名」「小写去空白标题」建三个哈希表，解析每条链接都是常数次查表。spike 里线性扫描用了 23.8 秒，不作为基线；正式实现要用 1 万篇样本重新测量，并进 NFR 基准。
- 增量：文档的路径、文件名、标题变化时，只重算引用了旧值或新值的边（实测 5.2ms）。

### 4.5 渲染

- 阅读模式：Go 渲染整篇 HTML，结果按（路径, revision）缓存；超过 1 MiB 不渲染。实测 100 KB 文档约 24ms（R-3）。
- 与旧版一致的行为（R-3 实测对照：一致 76 例，有意差异 30 例，结构差异 0 例）：
  - 原始 HTML 转义成文字显示；
  - frontmatter 当正文渲染；
  - 标题不生成 id，`#xx` 锚点点击无动作；
  - 链接分 3 类，wikilink 有 3 种状态；
  - 危险 href 一律不可点。
- 对话：回答按块切分，已封口的块只渲染一次，只重渲染末尾正在写的块（实测单帧约 350µs）。末尾未完成的表格和链接先收起。块在 Go 侧按约 16ms 合并后推送。R-4 实测在 50 条历史加 1 万字的规模下，按 token 推送也不卡，合并推送主要是为了语义清晰和降低消息数。
- 安全：渲染入口跑了 2 分钟 fuzz，共 105 万次，0 panic，输出里没有可执行内容。

### 4.6 AI 回合

- 引擎在 Go 进程内运行，每个回合一个 goroutine，用 `recover` 包住，单个回合出错只影响这个回合。
- 出站请求用 `netproxy.Transport()`；key 从 `mygo.Secrets` 读。
- 重试、空闲超时、工具循环、上下文预算、权限门等数值以 agnes-engine skill 和 PRD FR-AI-* 为准。
- 审批卡状态以 Go 为准：前端发出回应、收到确认后才移除卡片。

### 4.7 旧版数据衔接（R-7）

- 旧版应用数据目录：`%APPDATA%\mile-knowledge-base\`。2026-11-18 在本机只检查了文件是否存在、没有读内容：`settings.json`、`recent-documents.json`、`audit.json`、`engine-credentials.json`、`conversations/`，以及 8 个 `index-*.json` 都在。
- 首次启动时，只读导入 `settings.json`（主题、关窗行为、7 个布局字段、最近知识库，最多 12 个、上次知识库）和 `recent-documents.json`（每个知识库最多 12 条）；字段定义见旧版 `shared/settings.ts`、`shared/recentDocuments.ts`。不导入审计、对话、索引、凭据（D-003）。
- **知识库 id 必须沿用旧版算法**：真实路径转小写后取 SHA-256 的前 16 位十六进制（旧版 VaultService 中的 `vaultIdFor`）。否则导入的最近文档对不上知识库，同一个库在新旧版也会被当成两个库。
- 导入只读旧文件，不修改；解析失败按默认值运行，并在界面提示一次。
- 验证：用旧版 `scripts/verify-ui-m0.cjs` 同款的种子 settings.json 写成测试样本；不在测试中读用户真实文件。

## 5. 安全与隐私

以 PRD 10.2 节为准，实现要点：

- 路径：pathguard 两道校验；Agent 路径另加系统区禁写前缀（agnes-engine skill）。
- 导航：`OnWillNavigate` 只放行应用自身来源；http(s) 交 `Shell.OpenExternal` 打开；新窗口一律拒绝。
- 生产构建 `DevToolsDisabled`，同时会关掉 WebView2 自带的 F5、Ctrl+R 等快捷键。
- 图片协议只返回授权路径下、白名单格式的图片。Windows 上页面中的地址形式是 `http://<scheme>.localhost/...`（mygo `protocol.go:204`），协议名已定 `kbimg`（API.md §5）。
- key 只存在 `mygo.Secrets`；凭据管理器不可用时拒绝保存。
- 错误在 service 出口统一脱敏；日志不记正文和完整路径。

## 6. 运行、部署与可观察性

- 交付（M3 D-013 定稿）：`mygo build` 生成 Windows 安装包 `.exe`（NSIS，当前用户安装到 `%LOCALAPPDATA%\Programs`，无需管理员），首个发布版本 1.0.0（旧版为 2.7.0，新旧并存）；不配置自动更新；不做代码签名（没有证书，SmartScreen 警告记入发布清单的已知风险）。

### 13.3 真身探测

只查 CLI 不够：WorkBuddy、Antigravity、OpenCode 桌面版、DeepSeek Harness、ZCode、MiniMax Code 都没有 CLI。改为 3 条证据，命中任一条即「已检测到」：

1. CLI：`%APPDATA%\npm`、`~\.local\bin`、进程 PATH，扩展名按 `''/.exe/.cmd/.bat/.ps1` 匹配（同 skillkit `detect.ts`）。本机实例：`claude`、`codex`（nvm4w）、`cursor`、`trae`、`qoder`/`qodercli`、`grok`、`pi`、`kiro`/`kiro-cli`、`hermes`、`kimi`。
2. 注册表卸载项：读 `HKCU` 与 `HKLM`（含 `WOW6432Node`）的 `...\CurrentVersion\Uninstall`，按 `DisplayName` 前缀匹配，只读。本机实例：Cursor、TRAE、WorkBuddy、Qoder、OpenCode、Antigravity、Kiro、Warp、Kimi、Hermes Agent CN Desktop。
3. 已知安装位置的可执行文件，如 `%LOCALAPPDATA%\Programs\<名称>\<名称>.exe`。本机实例：DeepSeek Harness、ZCode、MiniMax Code。注意：本机的 `%LOCALAPPDATA%\Programs` 被重定向到 D 盘，所以要用 `SHGetKnownFolderPath(FOLDERID_UserProgramFiles)` 或卸载项里的 `InstallLocation`，不能硬拼 `C:\Users\...`。

每个工具具体匹配哪些名称，写进注册表代码并配单元测试；e2e 用注入的假注册表与假 PATH，不读真实环境。

### 13.4 本机现状带来的设计约束

- 本机工具目录里已经有大量链接：
  - 239 个符号链接指向 `~\.config\magpie\library\skills`；
  - 215 个目录联接指向 `~\.agents\skills`，分布在 Trae、Qoder、Windsurf、CodeBuddy、Kiro；
  - 本机还装着 Skillkit。
- 所以 PRD FR-SKM-SCAN 的来源状态要增加「链接到外部」：显示目标路径（脱敏），可以卸载（只删链接），可以收编（复制目标内容进知识库，可选把链接改指向知识库）；**目标目录一律不修改**（用户 2026-11-20 选择）。
- 识别链接要同时认符号链接与目录联接。R-9 实测：go1.27.3 的 `os.Lstat` 把联接报成 `ModeIrregular`（不是目录，也不是 `ModeSymlink`），这个行为在 Go 1.23 变过。所以识别用 `FILE_ATTRIBUTE_REPARSE_POINT` 加 `FSCTL_GET_REPARSE_POINT` 读标签与目标；`filepath.EvalSymlinks` 的返回值和目标字符串对不上，不用它。
- 创建：用 `FSCTL_SET_REPARSE_POINT` 写联接，不启动 `mklink` 子进程。内核不校验目标，所以创建前要求目标是本地绝对路径、存在且是目录；创建后经链接 `os.Stat` 一次，失败就删链接、退回拷贝。
- 删除时：对任何重解析点（符号链接、联接）只删链接本身，即确认是链接后 `RemoveDirectory`；备份与遍历用不进入重解析点的自写遍历。R-9 实测 go1.27.3 的 `os.RemoveAll` 遇到联接只删链接，但仍要加回归测试（含链接的目录被 `RemoveAll` 后链接目标哈希不变），防止 Go 或 `GODEBUG` 设置变化。
- 现有 `internal/vault/skillimport.go` 的 `walkSkill` 会跳过联接（`IsDir()` 与 `IsRegular()` 都为 false），技能导入不会读穿联接。
- 扫描量：本机最大的单个目录 71 个技能，所有工具合计约 700 个条目。R-9 基准（700 个条目，识别 + 读 `SKILL.md` 前 4 KiB）稳定在 60–85ms；刚写完文件的第一遍出现过 2.34s 的峰值（推测是杀毒软件扫描）。M4 计划据此定目标，界面先显示缓存结果。

## 14. R2 主题色：首帧与数据流（M3.5）

> 状态：用户 2026-11-20 审核通过；14.3 的 A-1 至 A-4 在 M3.5 首个任务里验证。对应 PRD 第 16 节、API.md 第 11 节、数据库设计 4.1.1。

### 14.1 为什么不用 localStorage

PRD 16.5 原先计划把主题色镜像到 `localStorage`，由 `public/theme-init.js` 在首帧前读出。mygo 文档写明开发版与打包版页面的 origin 不同，`localStorage` 不通用，并建议数据放在 Go 侧、经绑定交给页面（mygo v0.10.0 `docs/frontend.md:42-48`）。所以改用下面的方案，Go 的 `settings.json` 是唯一来源。

### 14.2 方案

1. Go 启动时读出 `settings.json` 的 `accent`（按数据库设计 4.1.1 规范化），在创建窗口时通过 `PageOptions.PreloadScript` 注入一行**只含数据**的脚本：`window.__MKB_ACCENT__ = <JSON>`。mygo 用 WebView2 的 `AddScriptToExecuteOnDocumentCreated` 在页面自己的脚本之前运行它（`window.go:811`、`internal/windows/webview.go:796`）。JSON 由 `encoding/json` 编码，不拼接字符串。
2. `public/theme-init.js`（已在 `<head>` 里、早于前端包运行）读这个值：预设直接设 `<html data-accent="…">`，由 CSS 的 `[data-accent]` 规则生效；自定义色有 `cache` 时设 `data-accent="custom"`，并把两组值写成 `<html>` 的 20 个内联变量（`--accent-light-*`、`--accent-dark-*`），由 `[data-accent='custom']` 与 `[data-theme='dark'][data-accent='custom']` 两段 CSS 映射到 10 个令牌，这样之后切换明暗也不用重算；没有 `cache` 时先不设，等前端包加载后由 `src/lib/accent.ts` 计算。
3. 用户在色板里换色：前端立即在页面上换色，然后调 M61 `patch`（自定义色时带上算好的 `cache`）。成功后 Go 写盘；下次启动的 PreloadScript 带的就是新值。`PreloadScript` 在窗口创建时设定、没有运行时修改的接口，所以本次运行内不需要更新它。
4. 配色算法只在 `src/lib/accent.ts` 一处实现；Go 不算颜色，只校验格式。

### 14.3 验证结果（M3.5 T00，2026-11-20）

结论：**方案成立，不需要替代方案**。证据在 `spikes/r10-preload/RESULT.md`；下表是结论摘要。

| 编号 | 问题 | 结论 |
| --- | --- | --- |
| A-1 | 生产 CSP 禁止内联脚本；宿主注入的 PreloadScript 是否受页面 CSP 限制 | **不受限**：页面内联脚本被拦（`inlineBlocked:true`），注入脚本照常执行 |
| A-2 | PreloadScript 是否早于 `<head>` 里的 `theme-init.js` | **是**：三次运行注入都早 4–7 ms，`theme-init.js` 读到值时值已存在 |
| A-3 | 首帧颜色 | **是**：`theme-init.js` 是阻塞式 head 脚本，同步设好属性；第一次 rAF 时按钮已是注入色，截图像素一致。WebView2 无 Paint Timing，验收用「第一次 rAF 的计算色 + 截图像素」（T07） |
| A-4 | 自定义色无 `cache` 时的跳变 | **降级为默认橙、不报错**；最差是首帧默认色随后换色，可接受 |
| A-5 | 值里含 `</script>`、引号与特殊空白 | 原样到达页面，`__PWNED__` 未定义；用 `encoding/json` 编码即可 |

- 知识库技能只取 `skills/<分类>/<技能>/SKILL.md`（与 FR-SKILL 一致）。
- 工具技能状态判定顺序：重解析点 → 目标在活动库 `skills/` 下 = 链接到知识库（目标不存在 = 链接失效）；目标在知识库外 = 链接到外部；否则查分发记录：有记录且路径一致 = 拷贝自知识库（按基线哈希算同步状态）；名字在注册表内置清单 = 内置；其余 = 独立。
- 拷贝同步状态：基线哈希 = 分发时记录的知识库内容哈希；当前工具内容哈希 = 知识库当前哈希 → 一致；工具哈希 ≠ 基线、知识库哈希 = 基线 → 工具里被改过；知识库 ≠ 基线、工具 = 基线 → 知识库有更新；两边都 ≠ → 两边都改；工具目录不存在 → 工具里那份不见了；知识库技能已删或改名 → 知识库已删除（孤立拷贝，不再提供重新分发）。
- 缓存：`scan-cache.json` 保存最近一次结果（含每个条目的 mtime/大小与哈希），打开时立即显示；扫描完成后整体替换。缓存损坏就删除重建。

### 15.5 分发、卸载、收编、恢复

- 分发方式：默认联接；创建前要求目标是本地绝对路径、存在且是目录，创建后经链接 `os.Stat` 一次，失败删链接并退回拷贝，结果里写明实际方式。用户显式选拷贝就直接拷贝。
- 同名冲突：知识库内跨分类同名 → `skill-conflict`，detail 给出另一处位置；工具目录已有同名但非本技能 → 预览标「目标已存在」，未选覆盖则不写；覆盖 = 备份原目录 → 写入新内容 → 记录。
- 覆盖内置：拒绝（`skill-protected`）。
- 卸载：链接只删链接；拷贝/独立/内置？内置拒绝。拷贝与独立整个目录移入备份区；恢复时原位置已有同名 → `skill-conflict`，不覆盖。
- 收编：复制进知识库（分类必填，规则同 FR-SKILL）；可选换链（默认勾选，内置不提供）；换链前把原目录移入备份区再创建联接（失败则恢复原目录并报错，知识库副本保留）；多工具内容相同可一次收编，其余工具各自换链。
- 操作记录：每次操作一条；恢复本身也记一条；备份被清理后，记录保留但 `restorable=false`。

### 16.2 GitHub 请求

只匿名访问（Q-SKM-1）。所有请求带 `User-Agent: Mile-Knowledge-Base/<版本>` 与 `Accept: application/vnd.github+json`（取 SHA 时用 `application/vnd.github.sha`，响应是纯 SHA 字符串，GitHub 文档 Commits API）。

| 用途 | 请求 | 计入匿名额度 |
| --- | --- | --- |
| 没写 ref 时取默认分支 | `GET api.github.com/repos/{o}/{r}` → `default_branch` | 是，1 次 |
| 取 ref 的头部提交 | `GET api.github.com/repos/{o}/{r}/commits/{ref}`（`Accept: application/vnd.github.sha`） | 是，1 次 |
| 取某个技能子目录的最近提交 | `GET api.github.com/repos/{o}/{r}/commits?sha={ref}&path={子路径}&per_page=1` | 是，每个技能 1 次 |
| 下载内容 | `GET codeload.github.com/{o}/{r}/tar.gz/{头部提交 SHA}` | 大概率不计（官方没写明），按「计入」估算 |

- 下载钉在头部提交 SHA 上，记录的 `commit` 与下载内容一定对应，不会在两次请求之间被新提交插队。
- 安装 N 个技能约 2 + N 次 API 请求；检查更新按 (owner, repo, ref, 子路径) 去重，每组 1 次。单轮检查最多 40 组，超出的标「未检查」并在底栏写明数量（不静默截断）。
- 额度：读 `x-ratelimit-remaining` / `x-ratelimit-reset`；返回 403 或 429 且剩余为 0 时立即停下这一轮，报 `rate-limited`，detail 带重置时间；不重试。
- 超时：连接 10 s、首字节 15 s、整次下载 120 s；网络错误重试 1 次（不像 skillkit 那样回退国内镜像：PRD 15.4 只允许连 GitHub）。
- 重定向只跟随到 `github.com`、`api.github.com`、`codeload.github.com`，最多 3 跳；其他主机一律拒绝。
- 404 报 `not-found`，提示「仓库或路径不存在；私有仓库在未登录时也显示为不存在」。
- 页面不直接访问 GitHub：所有外连在 Go 侧，CSP 的 `connect-src` 不变。「在 GitHub 打开」走已有的 `Shell.OpenExternal`。

### 16.3 下载与解包安全（不变量）

按优先级列出，实施时每条配单元测试：

1. **整包上限 200 MiB**（Q-SKM-5）：`Content-Length` 超出直接拒绝；流式计数，读到第 200 MiB 就中止。解开后的总量另计，超过 200 MiB 同样中止。条目数上限 20 000。
2. **路径**：tar 去掉第一层 `<repo>-<sha>/`；任何条目含 `..` 段、以 `/` 或 `\` 开头、含盘符或 `:`、含 Windows 保留名（CON、NUL…）、末尾是点或空格、与已出现的条目只差大小写，都**整包拒绝**（`unsafe-archive`，detail 给出第一个违规条目），删除暂存目录，不留残留（AC-SKM-13）。
3. **链接与特殊文件**：符号链接、硬链接、设备文件跳过，不创建；跳过的条目列在结果的 `skipped` 里。
4. **zip 先验后写**：先读中央目录把所有条目按第 2 条检查一遍，再解压；解压时仍按实际字节计数（不信头部声明的大小）。
5. **只写暂存区**：解包目标是 `skills/tmp/<stageId>/root/`，用 `ResolveUnder` 逐条解析；暂存区以外不写。
6. **不执行任何内容**：不读可执行位，解出的文件一律普通文件。
7. **单技能上限**沿用 FR-SKILL 的 2000 文件 / 50 MiB：超出的候选标「过大」，不能勾选。

| 远端变化 | 本地改过 | 显示 | 操作 |
| --- | --- | --- | --- |

### 16.6 更新执行

- **知识库技能**（M94 → 计划卡 → M95）：
  1. M94 下载新版本到暂存，与知识库里的技能目录逐文件比较，生成一条 `origin=user` 的变更计划：文本文件新增用 `create`、修改用 `edit`（带 `expectedTargetRevision`）；非 UTF-8 或超过 2 MiB 的文件用新增的 `importFile`；远端删除的文件用 `trash`。目录先 `createDirectory`。（实现澄清，2026-11-21：带 BOM 或 CRLF 的文本、没有扩展名的文件——`create` 会追加 `.md`——以及父目录还不存在的新增文件也走 `importFile`，保证执行后的字节与名字和暂存版本一致；`importFile` 执行时自动建父目录，所以计划里不一定出现 `createDirectory`。）
  2. 前端把计划交给计划卡（与 FR-PROV「从来源同步」相同路径，`useMutationStore.propose`），用户确认后 M30 执行，事务可从操作日志恢复（AC-SKM-15）。
  3. 执行完成后前端调 M95：Go 重新计算知识库技能的哈希，等于暂存版本的哈希才更新 `skill-sources.json`（`commit`、`pathCommit`、`baseHash`）；不等（部分失败或执行期间又被改）就不更新，状态仍是「有更新」。
  - 变动超过 500 项（M29 上限）时不生成计划，提示重新安装。
- **工具技能**（M96）：本地改过就拒绝；否则原目录先移入备份区（kind `update`），再把新版本拷入，写记录与日志；失败时把备份移回。

### 16.7 变更计划新增 `importFile`

- 形状：`{kind:'importFile', target, stageId, stagePath, stageHash, expectedTargetRevision?}`；`target` 已存在时是替换（必须带 `expectedTargetRevision`，属于破坏性操作，进事务并保存原内容）。
- 只允许 `origin=user`；Agent 计划里出现即 `permission-denied`，生成时与执行时各查一次（与 `permanentDelete` 的审批门同一层）。Agent 也没有能产生暂存 id 的工具。
- 执行时由 SkillService 注入的解析器把 `stageId + stagePath` 解析到 `skills/tmp/<stageId>/root/` 内部，校验 sha256 等于 `stageHash`，再用已有的 `copyFileVerified` 写入；暂存已过期报 `not-found`，提示重新检查更新。
- 风险等级：只新增 → low；含替换 → medium（与 `edit` 相同口径）。
- 事务格式不变：pre-image 本来就按 sha256 存任意字节。

### 16.8 测试与门禁

- 单元测试用 `httptest` 假 GitHub：默认分支、ref 头部、子目录提交、tar.gz、404、403 + 额度为 0、慢响应超时、跨主机重定向。
- 解包测试用运行时生成的恶意包：`../evil`、绝对路径、盘符、保留名、大小写冲突、符号链接、超大（200 MiB 边界用稀疏计数而不是真文件）、zip 头部谎报大小。

- 性能（G-PERF `kind=m5`，2026-11-21 实测）：本地假服务上 50 MB tar.gz 从读取到列出候选 p95 **204 ms**（5 次：190/178/182/204/192 ms，目标 3 s）；M93 检查 20 组 **69 ms**（目标 2 s，groups=20、unchecked=0）。阈值 `read50P95Ms` 3000、`check20Ms` 2000，阻断；脚本 `scripts/e2e/perf-m5.sh`。
- 真实 GitHub 冒烟（读一个公开仓库）属于外连，列为人工项，执行前单独征得同意（B-M5-02）。

### 16.9 已知限制

- 在知识库里改名或移动一个 GitHub 来源的技能后，`skill-sources.json` 的记录对不上路径，不再检测更新（与 FR-PROV 的来源记录同样限制）；记录保留，路径不存在时在下次写入该文件时清理。
- 私有仓库、GitHub Enterprise、Git LFS 文件不支持（匿名访问拿不到；LFS 指针文件会被当作普通文本装进来）。
- `/tree/<ref>/<path>` 里的 `ref` 只取一段（2026-11-21 实现澄清，API §13.3）：含斜杠的分支名（如 `feature/x`）会被解析成 ref `feature` + 路径 `x`，请求多半 404；这类仓库请直接用仓库地址（默认分支）。

### 17.3 登记与路径规则（不变量）

存储：`skills/targets.json`（格式见数据库设计 4.6 M6 增补）。保存与读取两次都校验，不信任前端。

路径规则（Q-M6-4 已批准只做本机路径）：

1. 必须是绝对路径且以盘符开头；拒绝 UNC（`\server\share`）、`\?\`、`\.\` 与相对路径 → `invalid-input`。
2. 目录必须已存在、是目录、**本身不是重解析点**（联接 / 符号链接）：先 `EvalSymlinks` 再判；登记目录里面的链接不影响（扫描与写入仍按第 15.3 节处理）。
3. 读写目标不能与任何已登记知识库的根目录重叠（相同、父、子，双向）→ `path-escape`。读写目标：自定义工具是它的目录本身；项目是它的每个约定子目录与 `installRel`（项目根**本身**不算——知识库放在项目里是正常情况，扫描与写入都不碰根目录）。这条挡住「项目根 / `installRel` 恰好是知识库」时绕过知识库写入规则。
4. 不能与内置工具的安装目录、只扫描目录、内置目录相同，也不能是它们的父目录或子目录 → `skill-conflict`。
5. 不能与另一个已登记目标重叠：自定义工具看它的目录；项目看**根目录与它的全部约定子目录**（否则先登记项目、再登记它的 `.claude/skills` 会把同一批技能列两遍）。相同、父、子都算重叠 → `skill-conflict`，detail 写冲突对象。
6. 比较用真实路径（`EvalSymlinks` 后的绝对路径），大小写不敏感（Windows）。登记目录不存在时按 `Clean` 后的绝对路径比较（删除登记目录后再登记同名路径仍能识别）。
7. 数量上限 100 个（自定义 + 项目合计），超出 `invalid-input`。

加载校验的范围（T12 审查澄清）：`targets.json` 读取时只做形状、字段与登记之间的重叠检查（目录只解析根路径，见 17.9 的 `targetDirsText`），不重建 VaultRoots / 内置目录环境；知识库与内置目录两条规则只在保存时强制。原因是读取发生在每次扫描前，逐条解析所有子目录会把扫描拖慢一个数量级（T11 实测）；手改文件绕过保存校验的记录仍受扫描期的链接来源判定约束。

名称规则：1–40 字符、单段（同 FR-SKILL 的单段规则：不以点开头、无保留名、无 `..`、无路径分隔符），不能与内置工具显示名相同，在已登记目标内不重名（大小写不敏感）→ `invalid-input`。

项目的安装子目录（Q-M6-1 已批准）：只能取该项目的约定子目录之一（17.2 的清单）；登记时默认取第一个**已存在**的约定目录，都不存在时用 `.claude/skills`；之后可编辑。扫描永远只读目录，写只在用户分发 / 安装时发生。

目录选择：沿用 M12 `pickFolder` 的令牌做法（M98）：Go 弹原生对话框，返回不透明 token（10 分钟、可重复使用到过期或保存成功为止），前端拿不到绝对路径，只拿到显示名与脱敏路径。

### 17.4 探测与扫描并入

- 自定义工具：登记即视为「已检测到」，生成一个 `DetectedTool`（`id` = 登记 id `t-<12 hex>`，`kind='custom'`）；目录不存在时 `missing=true`，分组照常显示但标注「目录不存在」，行数为 0。它的安装目录与扫描目录都是登记目录本身，wire spec 用 `install:<rel>`。
- 项目：一个项目生成**一个**分组（`id` = 登记 id，`kind='project'`），扫描它的约定子目录中**实际存在**的那些（加上 `installRel` 若它还不存在则不扫描、只作为写入目标）。每行带 `sourceToolId`（17.2 归属）与 `subdir`（项目内相对目录，如 `.claude/skills`）。
- 自定义与项目都并入现有的状态判定（15.4 六种来源）、缓存与警告逻辑；`scan-cache.json` 版本升为 2（旧缓存直接删除重建，派生数据）。
- 项目根下的其他目录、隐藏文件、点号目录一概不读；同一个物理目录不会因两个工具共用（如 `.agents/skills`）出现两次。
- 分组顺序：内置工具按注册表顺序 → 自定义工具（按创建时间）→ 项目（按创建时间）；chip 行同一顺序。

### 17.5 写路径扩展

- 目标解析：`toolId` 可以是内置 id 或登记 id（`t-` 开头）。登记 id 解析到 targets.json；解析失败 → `not-found`（提示登记已被移除）。
- wire spec：自定义工具同内置（`install:<rel>`）；项目新增 `project:<dir>:<rel>`，`<dir>` 是项目内约定目录原样（如 `.claude/skills`），`<rel>` 1–2 段、单段规则同 §12.3。服务端先按注册表顺序做最长前缀匹配（目录可能有多段，如 `.gemini/config/skills`），再校验 `<rel>`；`<dir>` 不在该项目的可写目录（约定目录 + `installRel`）→ `invalid-input`。
- 分发 / 安装到项目：写入 `<项目根>/<installRel>/<技能名>`；`installRel` 目录不存在时按需创建（与 Antigravity 安装目录按需创建同一做法）。目标已存在的规则同内置（跳过 / 覆盖先备份）。
- 卸载 / 收编 / 更新：对项目行与自定义工具行同内置规则；链接只删链接、内置保护、覆盖备份都不变（第 15.3、15.5、16.6 节）。
- 记录：`state.json`、`sources.json`、备份 `meta.json`、日志的 `toolId` 允许是登记 id；读入时记录指向不存在的登记 → 丢弃并记 warning（与 4.6 现有规则一致）。

### 17.6 移除登记（Q-M6-3 已批准）

1. 服务层操作锁内执行（与分发 / 卸载同一把锁 `opMu`，2026-11-22 T06 实施），避免与进行中的写入交错。
2. 删除 `state.json` 中 `toolId` 等于该登记 id 的分发记录，删除 `sources.json` 中同 id 的来源记录；**不触碰目录里的任何文件**。
3. 追加一条 `unregister` 日志（`toolId` = 登记 id、`location` = 脱敏路径、detail 写删除的记录数）。
4. 清扫描缓存，前端重新拉 M77 刷新（不依赖后台 goroutine 发出的 E12，见 1.3.1 结论）。
5. 重新登记同一目录后，留下的链接 / 拷贝会被扫描按哈希重新识别（链接到知识库 = linked，拷贝且内容一致 = copied），但原来的分发记录不会恢复。

### 17.7 安全与边界

### 18.4 目标键与匹配

- 目标键（写进清单的 `target`）：
  - 内置工具：`{kind:'builtin', toolId}`；
  - 自定义工具：`{kind:'custom', name}`；
  - 项目：`{kind:'project', name, subdir}`，`subdir` 取分发时的实际安装子目录（由 `targetPath` 相对项目根推出），不取登记当前的 `installRel`。
- 项的唯一性：同一份清单里「目标键 + 工具目录里的技能名」只有一项（与工具目录里一个位置一一对应）。名称比较不区分大小写。
- 本机匹配：
  - 内置：注册表里有这个 id，且 `Enabled`、已检测到（共享目录 `agents` 视为已检测到），否则跳过；
  - 自定义 / 项目：本机登记里同类型、名称相同（不区分大小写）的一项；登记目录不存在（`Missing`）也算未匹配；
  - 项目还要求 `subdir` 在 `ProjectSkillDirs()` 清单里，否则该项判为非法并忽略（18.7）。
- 目标目录：内置 / 自定义 = `InstallDir/<name>`；项目 = `<本机项目根>/<subdir>/<name>`。

### 18.5 还原判定

每一项按下面顺序判定，得到 `create` / `exists` / `conflict` / `skip`：

1. 目标未匹配（18.4）→ `skip`，原因「工具在本机未检测到」「工具未启用」「本机没有登记『<名称>』」「登记目录不存在」。
2. 知识库项：本机知识库 `<skillPath>` 不是含 `SKILL.md` 或 `AGENTS.md` 的目录 → `skip`「知识库里没有这个技能」。
3. 目标目录不存在 → `create`，默认勾选；GitHub 项另标 `needsNetwork`。
4. 目标目录存在：
   - 知识库项：是指向本机该技能目录的联接，或本机分发记录里有这个目标位置 → `exists`（方式与清单不同时原因写「本机为拷贝」或「本机为链接」）；
   - GitHub 项：本机来源记录里有这个目标位置，且 `owner/repo` 与子目录相同（不区分大小写）→ `exists`（提交不同不算不一致，更新走 FR-SKM-UPD）；
   - 是内置技能 → `skip`「内置技能不能覆盖」；
   - 其余 → `conflict`，默认不勾选，可勾选覆盖。
- 「本机有、清单没有」：本机分发记录中属于当前知识库（`vaultId` 相同）的项，加上全部工具来源记录，减去清单已覆盖的目标位置；只列名称与目标名，不参与执行。
- 横幅的 N = `create` 数 + `conflict` 数。`skip` 与 `exists` 不计入，避免永远消不掉的提示。
- 判定只读文件系统，不联网。

### 18.6 读入状态与重建

| 状态 | 条件 | 写清单 | 还原 | 重建 |
| --- | --- | --- | --- | --- |
| `missing` | 文件不存在 | 第一次写时创建 | 无项 | 可以 |
| `ok` | 可解析、`version` = 1 | 正常 | 正常 | 可以（会确认） |
| `unreadable` | JSON 解析失败（含 Git 冲突标记）或顶层结构不对 | 停写 | 不可（预览只显示状态） | 可以 |
| `too-large` | 文件超过 1 MiB | 停写 | 不可 | 可以 |
| `version-unknown` | `version` 不是 1 | 停写 | 不可 | **不可**（来自更新版本的应用，重写会丢字段；提示升级应用） |

- 单项不合法（18.7）只忽略该项并记 warning，整个文件仍是 `ok`。写入侧更严：`SaveManifest` 先整体校验，任一条不合法就拒绝写入（T01 实现与测试锁定），所以坏条目只会在读入时被丢掉，不会被写回文件。
- 重建：读本机分发记录中 `vaultId` 等于当前知识库的项、全部工具来源记录（目标位置仍存在的），按 18.4 生成目标键（登记已被移除的分发记录无法生成键，跳过并计数），整体写入。原文件存在时先改名为 `skill-distributions.json.corrupt-<UTC 时间>`（同目录），再写新文件；改名失败则不写，返回 `io-failure`。
- 上限：最多 2000 项，超出的项忽略并记 warning（写入时同样只写前 2000 项）。

### 18.7 安全

- 清单来自知识库，按不可信输入处理：
  - `skillPath` 必须匹配 `skills/<段>/<段>`（`IsValidKbSkillPath`），每段用 `IsValidSegment`；
  - `name` 用 `IsValidSegment`；`subdir` 必须在 `ProjectSkillDirs()` 清单里；`toolId` 必须在注册表里；
  - GitHub 项的 `owner` / `repo` / `ref` / `path` 用 `validOrigin`，`commit`、`pathCommit` 必须是 40 位十六进制；
  - 目标目录最后仍用 M4 的「解析到登记目录内部」校验（`resolveSpec` 同一口径），任何一步不过都不写盘。
- 写清单时只写 18.4 的字段，不写绝对路径、`vaultId`、机器名、用户名；单测断言序列化结果里不含驱动器号、`\Users\` 与当前用户名。
- 还原只写登记目录、备份区、暂存区与本机记录文件，与 PRD 15.4 相同；不删除任何东西（覆盖前移入备份区）。
- GitHub 项只请求 `codeload.github.com/<owner>/<repo>/tar.gz/<commit>`，不调用 `api.github.com`，因此不消耗匿名 API 额度；同一 `owner/repo/commit` 的多项只下载一次。
- Agent：清单在 `.mile-kb/` 下，已被 R1 的系统区规则保护（PRD AC-AI-1）；M102–M104 只给界面绑定，Agent 工具表不变。

### 18.8 执行（M103）

1. 在 `opMu` 内重新读清单并重新判定（预览可能已过期）；请求里的项 id 在新判定里找不到 → 该项 `skipped`「清单已变化」；状态变成 `exists` → `skipped`「已一致」；`conflict` 但请求未带 `overwrite` → `skipped`。
2. 先做知识库项（不联网），再按 `owner/repo/commit` 分组做 GitHub 项：每组建一个暂存、下载、解包，逐项取子目录，按拷贝分发装进目标，成功后写来源记录（`commit`、`pathCommit` 取清单值，`baseHash` 取装好后的哈希）；组处理完删暂存。
3. 每项独立成败；取消（AbortSignal）时已完成的项保留，未开始的项 `skipped`「已取消」，进行中的下载删暂存。
4. 每个成功或失败的项记一条日志：知识库项 `op='distribute'`、GitHub 项 `op='install'`，`detail` 写「从清单还原」（不新增操作类型，见 Q-M7-4）。
5. 有任何成功项时写本机分发记录、清扫描缓存、发 E12；前端执行完成后主动重新拉 M77 与 M102（不依赖后台 goroutine 发出的 E12，1.3.1 结论）。

### 18.9 性能

建议门槛（随 PLAN-M7 审批，进入 G-PERF 前需用户确认）：

| 场景 | 规模 | 建议门槛 |
| --- | --- | --- |
| M102 预览 | 清单 200 项（150 知识库项 + 50 GitHub 项），本机 25 个内置工具 + 10 个登记目标 | p95 ≤ 300 ms |
| 清单写入（一次分发后的 upsert） | 清单 2000 项 | p95 ≤ 50 ms |
| M103 还原知识库项 | 100 项，链接方式 | 总耗时 ≤ 3 s |

实测（2026-11-23，`perf-m7.sh`，e2e 构建）：预览 200 项 p95 60.8 ms；清单写入净增量（2000 项清单分发与 1 项清单分发各 10 次，取逐对差值）p95 36.0 ms；还原 100 个知识库项 76.3 ms。首测 424.7 ms / 4552.9 ms，定位到重建逐条读登记表、还原逐项重建探测事实，改为每轮一次后达标。M6 的 `kind=m6` 复测（空载）基准 132.9 ms、项目 277.6 ms、保存 35 ms、移除 20.3 ms，全部在 M6 门槛内；负载较高的三轮回测基准最高 206.5 ms 超自身门槛，判定为整机负载。

GitHub 项受网络影响，不设门槛，只记实测。
